## ب. التشغيل المحلي

```bash
# الخادم، من backend/ (Python 3.12)
python -m venv .venv && .venv/Scripts/python -m pip install -r requirements.txt
cp .env.example .env        # المفتاح اختياري؛ بدونه يعمل البحث بالقواعد
python -m uvicorn app.main:app --port 8000
# الواجهة، من frontend/ (اختُبرت مع Node 24 وnpm 11)
npm ci && npm run dev       # VITE_API_BASE_URL افتراضيًا http://localhost:8000
```

**الاعتماديات:** 6 حزم مثبتة الإصدارات في `backend/requirements.txt`. الواجهة تُبنى من `frontend/package-lock.json`.

**المتغيرات:**
- `FURSAH_ALLOWED_ORIGINS`: الأصول المسموحة في CORS.
- `FURSAH_EVALUATION_TIME`: فارغ يعني الوقت الفعلي.
- `FURSAH_MODEL_*`: اختيارية، وتحمل مفتاح النموذج إن وُجد.
- `FURSAH_TRACE_JSONL_PATH`: فارغ يعني بلا ملف تتبع.

## ج. النشر

| البند | القيمة |
|---|---|
| المنصة | Render، Web Service |
| رابط الخادم | `https://fursah.onrender.com` |
| خادم التطبيق | `uvicorn`، من ترويسة `x-render-origin-server: uvicorn` |
| طريقة البناء والتشغيل | **غير متحقق منها من Render.** في المستودع `Dockerfile` معدّ لـ Render، ويشغّل `uvicorn app.main:app --host 0.0.0.0 --port ${PORT}`، ويضمّن `backend/app` و`data/` |
| رابط الواجهة | لم تُنشر |

**نقاط API:**
- `GET /health`
- `GET /ready`
- `GET /docs`
- `POST /api/v1/discover`
- `GET /api/v1/opportunities/{id}`، ويقبل معرّف الفرصة أو معرّف المصدر.

**الإعدادات المستنتجة من السلوك، لا من لوحة Render:**
- `FURSAH_EVALUATION_TIME` غير مضبوط: الفلاتر تعرض وقت الطلب الفعلي.
- لا نموذج مفعّل: لا تظهر عبارة «بمساعدة النموذج» في الفلاتر.
- `FURSAH_ALLOWED_ORIGINS` على القيمة الافتراضية (`localhost:5173`): أصل خارجي يُرفض في preflight بـ 400.

**الأسرار:**
- تُضبط من Environment في لوحة Render فقط.
- لا شيء منها في Git ولا في هذا التقرير.
- الواجهة لا تحتاج أي سر؛ `VITE_API_BASE_URL` عنوان عام.

**ملاحظة:** ملفات Vercel في المستودع لا تؤثر على Render، وتجربة Vercel لم تُعتمد. على GitHub حالة نشر ناجحة لمشروع Vercel باسم `fursah-api` على `36d5c53`، أُنشئ من لوحة Vercel، ولم يُفحص.

## د. التحقق

كل الطلبات أُرسلت فعليًا بـ `curl` إلى `https://fursah.onrender.com`.

### نجح

| الاختبار | النتيجة | الدليل |
|---|---|---|
| `GET /health` | `{"status":"ok","service":"fursah-api"}` | HTTP 200، في 22.4 ث لأن الخدمة كانت خاملة |
| `GET /ready` | `storage` و`application` = true | HTTP 200 |
| `GET /docs` و`/openapi.json` | واجهة Swagger وملف المخطط | HTTP 200 |
| بحث فعلي (طلب DEV-01: «إدارة مشروع صغير في مكة المكرمة») | `ok`، توصية واحدة: SRC-0370، عن بُعد | HTTP 200، في 0.63 ث |
| تعارض الطلب مع التفضيل (طلب TEAM-01: «ورشة في جدة» مع تفضيل الرياض) | `needs_info`، مع `constraint_conflict=true` و`constraints.location_preference` | HTTP 200 |
| طلب غير صالح (`query` فارغ) | `FURSAH_REQUEST_VALIDATION_ERROR` | HTTP 422 |
| تفاصيل SRC-0370 | `opp-95ec84b9aed5`، «إدارة مشروع صغير للمهتمين» | HTTP 200 |
| تفاصيل SRC-0081 | `closed`، والموعد 2026-10-19 | HTTP 200 |
| معرّف غير موجود (SRC-9999) | — | HTTP 404 |
| CORS للأصل المحلي | `access-control-allow-origin: http://localhost:5173` | ترويسة على POST فعلي |

**صحة المحتوى:**
- النتائج مأخوذة من البيانات الفعلية، والبصمة مطابقة للملف المحلي.
- نتيجة DEV-01 تطابق تشغيلًا محليًا بالوقت الفعلي ومن دون نموذج: SRC-0370 فقط.
- SRC-0081 هو الإجابة الموسومة بوقت المعسكر (2026-10-18)، لكنه يُستبعد الآن لأن موعده انتهى في 2026-10-19. هذا سلوك صحيح للوقت الفعلي، لا خطأ نشر.

### فشل أو قيد فعلي

| الاختبار | النتيجة |
|---|---|
| preflight من أصل واجهة خارجي | HTTP 400، بلا `access-control-allow-origin`. واجهة منشورة على نطاق آخر ستُحجب حتى يُضبط `FURSAH_ALLOWED_ORIGINS` |
| البدء البارد | 22 ث لأول طلب بعد الخمول (خطة Render المجانية تُسكن الخدمة) |

## هـ. الواجهة الأمامية (الخطوة التالية)

إنشاء **Static Site** على Render من نفس المستودع:

| الحقل | القيمة |
|---|---|
| Root Directory | `frontend` |
| Build Command | `npm ci && npm run build` (من `package.json`: `tsc -b && vite build`) |
| Publish Directory | `dist` |
| Environment | `VITE_API_BASE_URL=https://fursah.onrender.com` (يُقرأ وقت البناء، ويجب أن يكون أصلًا بلا مسار) |

بعدها في خدمة الخادم: `FURSAH_ALLOWED_ORIGINS=https://<رابط الواجهة>`. يمكن إبقاء `http://localhost:5173` معه مفصولًا بفاصلة. ثم إعادة التحقق من preflight والبحث عبر الواجهة.

## و. إعادة النشر والتعافي

**إعادة النشر:** Manual Deploy في الخدمة. اختر Deploy latest commit، أو Deploy a specific commit لإصدار معروف. ومع Auto-Deploy، كل push إلى `main` ينشر تلقائيًا.

**الخطة:**
1. **متى يُعدّ الإصدار فاشلًا:** عند أي مما يلي:
   - `GET /ready` ≠ 200.
   - طلب DEV-01 لا يعيد `ok` مع SRC-0370 بالوقت الفعلي، أو مع SRC-0081 بوقت المعسكر.
   - طلب TEAM-01 لا يعيد `needs_info`.
   - أخطاء أو Tracebacks في Logs.
   - فشل النشر في Events.
2. **تحديد الإصدار السليم:** آخر Deploy في Events نجح فيه الفحص السابق. يُطابَق الـ commit المعروض هناك مع `git log`، و`evidence_version` مع البيانات.
3. **الرجوع:**
   - من Events: اختر النشر السليم ثم **Rollback**.
   - أو Manual Deploy، ثم Deploy a specific commit.
   - أوقف Auto-Deploy مؤقتًا حتى لا يعيد push جديد الإصدار المعطوب.
   - في Git: `git revert <commit>` ثم push عادي. لا `reset` ولا `force`.
4. **التحقق من الاستعادة:** أعد فحوص البند 1 على `https://fursah.onrender.com`، ثم بحثًا من الواجهة عند نشرها.
5. **المخاطر:**
   - **متغيرات البيئة ليست جزءًا من الإصدار.** الرجوع لا يعيدها، فسجّل أسماءها وقيمها غير السرية قبل أي تغيير.
   - **رابط الخادم في الواجهة.** تغيير `VITE_API_BASE_URL` يتطلب إعادة بناء الواجهة.
   - **البيانات للقراءة فقط وضمن الإصدار.** لا قاعدة بيانات ولا خطر فقدان. القرص مؤقت، فلا يُعتمد على ملف التتبع إن فُعّل.
6. **ما يُسجَّل بعد التعافي:**
   - وقت العطل وعَرَضه.
   - النشر الفاشل والنشر المستعاد، كلاهما بالمعرّف والـ commit.
   - نتائج فحوص البند 1.
   - أي تغيير في المتغيرات.

**حدود الخطة:** موثقة وغير مختبرة. لم يُنفذ Rollback فعلي، ولم أتحقق من شاشة Events بنفسي.
